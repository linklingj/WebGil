# 02-R. 구조 추출 엔진 — 현황 점검과 개선안

> 기준 코드: `packages/core/src/structure.ts`, `packages/core/src/dom-semantics.ts` (2026-08-05).
> 측정: `pnpm --filter @webgil/bench observe` + 손실/시간 계측. 스펙은 [`02_structure-extraction.md`](02_structure-extraction.md).

## 1. 지금 어떻게 만들고 있나

한 문장으로: **"의미 있어 보이는 요소만 선택자로 뽑아 평평한 목록을 만든 뒤, 헤딩 레벨 스택으로 계층을 다시 세운다."**

```
doc.querySelectorAll(SIGNIFICANT_SELECTOR)   ← 문서 순서대로 1회 순회
  → UI 루트 제외 · isHidden 제외 · roleOf → kindOf 로 종류 판정
  → landmark면 stack 리셋 후 root 직속 그룹으로
  → heading이면 레벨 비교로 stack push/pop
  → 나머지(link·button·input·img)는 현재 열린 섹션에 leaf로 붙임
  → prune: 빈 그룹 제거 → dedupeLeaves → bucketByKind
  → assignDepth
```

핵심 성질 4가지:

| 성질 | 코드 | 결과 |
|---|---|---|
| **선택자 화이트리스트** | `SIGNIFICANT_SELECTOR` (`dom-semantics.ts:5`) | 목록에 없는 태그는 **존재 자체가 사라진다** |
| **평면화 후 재구성** | `extractTree`의 단일 for 루프 | DOM의 컨테이너 중첩(카드·리스트 아이템)이 **전부 소실**, 헤딩·landmark만이 유일한 계층 근거 |
| **landmark = 최상위 리셋** | `structure.ts:118` `stack.length = 1` | landmark는 항상 root 직속. 문서 순서대로 chrome(헤더·내비)이 앞자리 차지 |
| **양 줄이기 = 사후 정리** | `dedupeLeaves` + `bucketByKind` | 무엇이 본문인지 판단하지 않고, 많으면 묶고 같으면 지운다 |

## 2. 실측 (SSR 페이지, jsdom 경로)

| 페이지 | 선택자 매칭 | 트리 노드 | a[href] → link | 문단성 요소(p 문자) → text | 추출 시간 |
|---|---|---|---|---|---|
| 위키백과 "대한민국" | 3,960 | 3,294 | 3,499 → 3,061 | 1,842개(**49,967자**) → **9** | 169.5ms |
| 세종대 공지 | 1,278 | 1,158 | 1,241 → 1,128 | 1,693개(2,678자) → 7 | 42.6ms |
| 야놀자 | 366 | 210 | 127 → 108 | 27개(89자) → 57 | 13.1ms |
| 안전운전 통합민원 | 200 | 174 | 61 → 48 | 173개(519자) → 4 | 6.3ms |

트리 개요 예시(세종대):

```
[group] 머리말 → [group] 링크 259개
[group] 탐색  → [group] 링크 294개
[group] 본문  → [heading] 세종소개 (8)      ← 정작 공지 목록은 여기 없음
[group] 바닥글 → [group] 링크 98개
```

> 주의: jsdom은 레이아웃이 없어 `isHidden`이 속성만 본다(`dom-semantics.ts:151`). 실제 브라우저에선 `checkVisibility`가 접힌 메가메뉴를 걸러 숫자가 개선된다. 다만 **아래 진단 1·2·4는 가시성과 무관**하다. 그리고 7개 테스트 사이트 중 3개(오픈소스대회·홈택스·무신사)는 JS 렌더라 jsdom에서 **노드 0** — 즉 지금 벤치는 절반을 측정하지 못한다.

## 3. 진단 — 심각도 순

### ~~P0-A. 본문 텍스트가 트리에 아예 없다~~ → 해결 (A-1 적용)

아래는 문제 기록. 조치 결과는 [§6](#6-조치-기록)에 있다.


`SIGNIFICANT_SELECTOR`에 `p·li·td·dd·blockquote·figcaption`이 없다. `kindOf`에서 `text` kind를 만드는 경로는 **`img[alt]` 하나뿐**(`structure.ts:59`).

- 위키백과 5만 자 본문 → text 노드 9개(전부 이미지 alt).
- 즉 지금 트리는 "문서"가 아니라 **링크·버튼 목록**이다. 헤딩으로 drill-down해서 도착하면 읽을 내용이 없다.
- WebAIM 조사에서 사용자가 헤딩으로 훑는 이유는 **그 아래 본문을 읽기 위해서**다([`03_RESEARCH/reference.md`](../03_RESEARCH/reference.md)). 현재 구조는 목적지가 비어 있다.

**이게 마음에 안 드는 느낌의 8할이라고 본다.** 나머지는 이 위에 얹힌 문제다.

### P0-B. 노이즈 제거가 계획만 있고 구현이 없다

스펙 §파이프라인 3단계 "`@mozilla/readability`류로 본문 분리"가 코드에 없다. `prune`은 본문/비본문을 구분하지 않는다. 결과가 위 표의 링크 편중이다 — 세종대 트리의 97%(1,128/1,158)가 링크이고, 그중 651개가 헤더·내비·푸터 메가메뉴다.

### P1-C. 평평한 버킷 = 탐색 불가능한 덩어리

`bucketByKind`는 같은 kind leaf 6개 이상을 **하나의 평평한 그룹**으로 묶는다(`structure.ts:174`에 이미 ponytail 표시). "링크 294개" 버킷에 들어가면 `Alt+↓`를 294번 눌러야 끝이다. 묶어서 **개수만 줄었고 탐색 비용은 그대로**다.

### P1-D. 컨테이너 구조가 소실된다

평면 순회라서 "카드 = 이미지 + 제목 + 가격 + 링크"라는 묶음이 남지 않는다. 야놀자에서 숙소 카드 하나가 링크 1개 + 텍스트 조각들로 흩어져, 어느 가격이 어느 숙소인지 트리만으로는 알 수 없다. 헤딩 없는 목록형 페이지(쇼핑·검색결과)는 **계층 근거가 0**이라 전부 한 레벨에 쏟아진다.

### P1-E. 최상위가 페이지 chrome으로 채워진다

landmark를 만나면 무조건 root 직속(`stack.length = 1`). 문서 순서상 header·nav가 먼저라 **사용자가 처음 만나는 최상위 항목이 늘 "머리말 / 탐색"**이다. 본문 우선 정렬이나 "본문으로 바로" 개념이 없다. 위키백과에서 최상위 13개 중 실제 문서는 뒤쪽 1개.

### P2-F. dedupe가 서로 다른 대상을 지운다

`dedupeLeaves`는 같은 부모 안에서 (kind, text)가 같으면 지운다. 목록 페이지의 "자세히 보기" × 20, "다운로드" × 12는 **텍스트만 같고 대상이 다르다** → 1개만 남고 나머지 19개는 사용자가 도달할 방법이 없어진다. 접근성 도구에서 이건 품질 문제가 아니라 **기능 손실**이다.

### P2-G. 버킷 노드 id가 매 추출마다 새로 발급된다

`bucketNode`는 `g${groupSeq++}`(`structure.ts:93`), `groupSeq`는 모듈 전역이며 리셋되지 않는다. 재추출 때 같은 버킷이 다른 id를 받으므로, **버킷 노드 위에 커서를 둔 상태에서 DOM이 바뀌면** `replaceTree`가 그 id를 못 찾아 상위 landmark로 튕긴다(`navigation.ts:121`). 요소 기반 노드는 `ensureNodeId` 덕에 안전하니, 버킷만의 문제다.

### P2-H. 매 mutation마다 전량 재추출

위키백과 대형 문서 기준 169ms + 디바운스 200ms. 무한 스크롤·라이브 영역이 있는 페이지에서는 계속 재추출한다. 스펙의 "증분 갱신 Phase 3"과 같은 항목.

### P2-I. `getAXTree()`가 실제로 쓰이지 않는다

`extractTree(doc)`는 DOM만 본다. `CaptureSource.getAXTree()`는 같은 `dom-semantics` 휴리스틱을 평평하게 다시 돌린 것이라 **정보량이 0**이고 아무도 호출하지 않는다. 스펙의 "DOM + AX 병합"은 미구현이며, 확장에서 진짜 AX 트리를 얻으려면 `chrome.debugger`의 `Accessibility.getFullAXTree`가 필요하다.

## 4. 개선안

### 4.1 방향 선택

| 안 | 내용 | 비용 | 효과 |
|---|---|---|---|
| **A. 현행 파이프라인 보강** | 선택자에 텍스트 블록 추가 + 본문 영역 한정 + 버킷 페이징 | 작음(~150줄) | P0-A·P0-B·P1-C 해결 |
| **B. DOM 재귀 순회로 재작성** | 컨테이너를 실제로 따라가며 "의미 없는 래퍼 접기" | 큼(엔진 교체) | 추가로 P1-D 해결 |

**A를 먼저, B는 Phase 3.** A만으로 체감의 대부분이 해결되고, B는 A가 만든 텍스트 노드 위에서 설계해야 판단 기준이 생긴다.

### 4.2 A안 — 4개 작업

**A-1. 텍스트 블록을 1급 노드로 (P0-A)**

- `SIGNIFICANT_SELECTOR`에 `p, li, dd, blockquote, figcaption, td` 추가.
- 텍스트 노드 진입 조건을 규칙으로 둔다: 자기 자신이 이미 트리에 들어간 다른 요소의 조상이면 건너뛰고(링크만 든 `li` 중복 방지), 순수 텍스트 길이가 임계값(예: 2자) 미만이면 버린다.
- 낭독 단위는 **문단 하나**. 긴 문단은 트리에서 자르지 말고 TTS 쪽에서 문장 단위로 끊는다(트리는 의미 단위 유지).
- 검증: 위키백과 문서에서 `text` 노드 수 ≈ `p` 수, 헤딩 아래에 본문이 붙는지.

**A-2. 본문 영역 판정 (P0-B, P1-E)**

- `@mozilla/readability`를 그대로 얹으면 **DOM 핸들이 끊긴다**(스펙이 지적한 그대로). 대신 **점수만 빌린다**: 후보 컨테이너별로 텍스트 길이 / 링크 텍스트 길이 비율(link density)을 계산해 본문 컨테이너를 고르고, **트리 생성은 지금처럼 원본 DOM에서** 한다 → 핸들 유지.
- 고른 본문 컨테이너를 트리 최상위 첫 자식으로 올리고, 나머지 landmark(header·nav·footer)는 그 뒤에 둔다. 사용자가 처음 만나는 항목이 본문이 된다.
- 임계값은 상수로 빼고 벤치로 튜닝한다(`GROUP_MIN`처럼).

**A-3. 버킷을 페이지로 쪼개기 (P1-C)**

- 버킷 크기 상한(예: 20). 초과하면 `링크 294개 > [1–20] [21–40] …` 2단으로 나눈다. 탐색 깊이 +1, 키 입력 294 → 최대 35.
- 버킷 id를 **내용 기반으로 안정화**(P2-G): `g0` 대신 `부모id:kind:페이지번호` 같은 결정적 id. 전역 카운터 제거.

**A-4. dedupe 조건 강화 (P2-F)**

- (kind, text)만 보지 말고 **링크 목적지까지** 본다: `a[href]`는 href가 같을 때만 중복. 버튼은 텍스트가 같아도 지우지 말고 남긴다(대상이 다를 수 있다).
- 그래도 남는 진짜 반복(사이트 전역 내비 중복)은 A-2의 본문 판정으로 걸린다.

### 4.3 B안 스케치 (Phase 3)

DOM을 재귀로 내려가며 각 요소를 세 갈래로 분류한다: **의미 노드**(헤딩·상호작용·텍스트 블록) / **컨테이너**(자식이 2개 이상 의미 노드를 가짐 → 그룹으로 남김) / **래퍼**(의미 노드 1개만 감쌈 → 접어서 삭제). 이 "접기" 규칙 하나로 카드·리스트 구조가 자연스럽게 보존되고, 헤딩이 없는 페이지에도 계층이 생긴다. 지금의 헤딩 스택은 이 트리 위에 "헤딩이 있으면 그 아래를 종속시킨다"는 후처리로 남긴다.

### 4.4 측정 기반 정비 (선행 조건)

개선을 **눈으로 말고 숫자로** 확인하려면 벤치가 먼저 고쳐져야 한다. 지금은 JS 렌더 사이트 3/7이 노드 0이고, jsdom이라 가시성 판정이 실제와 다르다.

- `tools/bench`를 **Playwright 경로로 전환**(스펙에 이미 `PlaywrightSource`로 예정됨). 실제 렌더 후 추출 → 확장과 같은 조건.
- 지표를 고정한다: `본문 문자 수 / 트리 text 문자 수`(본문 커버리지), `링크 비율`, `최상위 항목 수`, `본문 도달까지 필요한 키 입력 수`, `추출 시간`. 지금 값이 baseline.

## 6. 조치 기록

### A-1 본문 텍스트 블록 (완료)

- `TEXT_BLOCK_SELECTOR = p,li,dd,dt,blockquote,figcaption,td,pre`를 `SIGNIFICANT_SELECTOR`에 추가.
- `blockText(el)`이 블록의 텍스트를 두 값으로 낸다 — `text`(낭독용, 문장 중간 링크 포함)와 `proseLength`(링크·버튼 텍스트를 뺀 순수 문장 길이). **길이는 proseLength로 판정하고 낭독은 text로** 한다:
  - `<li><a>메뉴</a></li>` → proseLength 0 → 버림(그 링크는 자기 노드로 이미 있다).
  - `<p>자세한 내용은 <a>문서</a>를 보라.</p>` → 문장이 끊기지 않게 통째로 읽고, 링크는 별도 노드로도 남는다.
  - 중첩 블록(`li > p`)은 안쪽만 노드가 된다(같은 문장 중복 금지).
- 본문 블록에는 `MAX_NAME`(200자) 절단을 적용하지 않는다 — 자르면 내용이 사라진다. 긴 문단 분할은 TTS(05)의 몫.
- **문단은 버킷으로 묶지 않는다**(`BUCKET_KINDS`에서 `text` 제외). 묶으면 헤딩에서 내려와도 읽을 게 없는 원래 문제가 그대로 재현된다.

측정 (jsdom 경로, 위키백과 "대한민국"):

| 지표 | 전 | 후 |
|---|---|---|
| text 노드 | 9 (전부 img alt) | **526** |
| 본문 문자 수 | ~0 | **65,145** (페이지 p 문자 49,961 대비 130% — li·td·인용까지 포함) |
| 트리 노드 | 3,294 | 3,812 |
| 추출 시간 | 169.5ms | **253.0ms** |

- 추출 시간 +50%는 선택자 매칭 대상이 3,960 → 5,802개로 늘어난 대가다. 대형 문서에서 250ms는 mutation마다 반복하기엔 무겁다 → **P2-H(증분 재추출)의 우선순위가 올라갔다.**
- 다음은 §5의 2번(벤치 Playwright 전환). 지금 숫자는 SSR 경로 기준이고, 실제 브라우저에서는 `checkVisibility`가 접힌 메뉴를 걸러 노이즈가 더 줄어든다.
