# 구조 기반 스크린리더: 웹길

> 웹사이트를 구조적으로 재구성해, 시각장애인이 문서를 "훑어" 탐색하고 자연스러운 음성으로 듣는 오픈소스 스크린리더

---

## 1. 한 줄 요약

웹페이지를 시각적 픽셀 순서가 아니라 **의미적 문서 트리**로 재구성하여, 사용자가 최상위 레벨에서 세부 내용으로 계층적으로 내려가며 탐색하고, 트랙패드 제스처와 LLM 명령으로 조작하며, 최신 TTS로 듣는 접근성 도구.

---

## 2. 문제 정의

기존 스크린리더(NVDA, JAWS, VoiceOver)는 강력하지만 다음 한계가 있다.

- **선형 탐색 중심**: DOM/시각 순서를 따라 위→아래로 읽어, 페이지의 전체 구조를 파악하기 어렵다. 원하는 정보까지 도달하는 데 많은 키 입력이 필요하다.
- **구조 정보의 신뢰성 부족**: 실제 웹사이트의 heading·landmark 마크업이 부정확하거나 누락된 경우가 많아, 시맨틱 탐색이 제대로 동작하지 않는다.
- **기계적인 음성**: 전통적 TTS는 톤이 단조롭고 장시간 청취 피로가 크다.
- **높은 학습 곡선**: 수십 개의 단축키 조합을 외워야 한다.

**핵심 통찰**: 시각장애인에게 필요한 것은 "화면에 보이는 것을 그대로 읽어주는 것"이 아니라, **문서의 논리적 구조를 빠르게 파악하고 원하는 곳으로 점프할 수 있는 능력**이다.

---

## 3. 솔루션 개요와 차별화 요소

### 3.1 웹사이트의 구조적 재구성 (핵심 차별점)

원본 웹페이지를 파싱해 **계층적 문서 모델**(마크다운 트리와 유사)로 변환한다.

- 같은 레벨의 heading·섹션을 하나의 그룹으로 묶는다.
- 사용자는 문서의 **최상위 레벨(목차 수준)에서 시작**해, 관심 있는 항목에서만 하위 레벨로 들어간다.
- 시각 레이아웃이 아닌 **의미 기반 트리**이므로, "전체 → 세부"로 자연스럽게 좁혀가는 탐색이 가능하다.

재구성 파이프라인:

1. **DOM 수집 + 접근성 트리(AX Tree) 병합**: 시맨틱 태그, ARIA 속성, landmark 추출.
2. **구조 복원**: 마크업이 부실한 페이지는 휴리스틱(폰트 크기·굵기·위치·반복 패턴) + 선택적으로 LLM 보정을 통해 heading 레벨과 섹션 경계를 추론.
3. **노이즈 제거**: 광고, 반복 내비게이션, 푸터 등 본문과 무관한 요소 분리(Readability류 알고리즘 활용).
4. **정규화된 트리 출력**: 레벨(H1~H6 상당), 텍스트, 상호작용 요소(링크·버튼·입력창)를 노드로 표현.

> **도구 선택 — 규칙 기반 1차, 신경망은 폴백.** 1차 경로는 라이브 DOM을 직접 순회하는 규칙 기반(heading/landmark 파싱 + `@mozilla/readability`)으로 간다. 이유는 (1) 빠르고 결정론적이라 실시간·SPA 갱신에 견디고, (2) **원본 DOM 노드 참조를 그대로 보존**해 이후 "로그인창 눌러줘" 류 액션 실행(§3.4)에 바로 쓸 수 있기 때문. `ReaderLM-v2`(신경망 HTML→Markdown)는 규칙 기반이 실패하는 마크업 불량 사이트용 **로컬 폴백**으로만 둔다 — 단 (a) 라이선스가 CC-BY-NC(비상업)이라 상업화·재배포 제약, (b) 1.5B라 GPU 없으면 풀 페이지 변환이 수십 초로 핫패스 부적합, (c) MD 변환 시 라이브 DOM 노드 핸들이 사라져 낭독 트리엔 써도 조작 경로엔 못 씀. Jina의 호스티드 `r.jina.ai` API는 인증 페이지를 외부 서버로 보내고 세션과 무관하게 재fetch하므로 **런타임엔 쓰지 않고 오프라인 벤치마킹 용도로만** 쓴다.

### 3.2 트랙패드 기반 "점자 훑기" 내비게이션

노트북 트랙패드를 점자책 읽듯 사용하는 것을 기본 가정으로 한다.

- **좌 → 우, 위 → 아래로 훑으면**, 현재 레벨의 노드들을 순서대로 읽어준다(같은 레벨 단위 탐색).
- **스페이스(또는 지정 제스처/키)로 하위 레벨 진입** → 선택한 노드의 자식들로 컨텍스트 이동.
- **반대 제스처/키로 상위 레벨 복귀**.
- 손가락 위치와 노드 순서를 매핑해, "지금 어디에 있는지"에 대한 공간감을 제공.

> 설계 원칙: 소수의 직관적 제스처만으로 전체 탐색이 가능해 학습 곡선을 낮춘다.

### 3.3 최신 자연스러운 TTS

- 텍스트 노드를 자연스러운 최신 음성으로 낭독.
- **음성 스타일 선택 기능**: 여러 보이스/톤/속도 프리셋 제공.
- **로컬 및 API TTS 모두 지원**: 오프라인·프라이버시 우선 사용자는 로컬 엔진, 최고 품질을 원하는 사용자는 클라우드 API를 선택.

### 3.4 LLM 기반 자연어 내비게이션

- 예: "로그인창 들어가줘" → 페이지 구조를 이해한 LLM이 해당 요소를 찾아 포커스를 이동하고 실행.
- "가격 정보 요약해줘", "장바구니 버튼 눌러줘" 같은 명령도 처리.
- **로컬 LLM과 API LLM 모두 지원**: Ollama 등 로컬 모델과 OpenAI/Anthropic 등 API를 플러그인처럼 교체.

## 4. 시스템 아키텍처

```
[웹페이지]
   │  CaptureSource 어댑터  (기본: 확장 · 확장형: 데스크톱 · 개발/벤치: 헤드리스)
   ▼
[구조 추출 엔진] ── DOM + AX Tree + 휴리스틱/LLM 보정
   │
   ▼
[문서 트리 모델] ── 레벨·텍스트·상호작용 노드
   │
   ├──▶ [내비게이션 엔진] ◀── 트랙패드 제스처 / 키보드
   │           │
   │           ├──▶ [TTS 엔진 추상화] ── 로컬 | API (스타일 선택)
   │           │
   │           └──▶ [LLM 명령 엔진] ── 로컬 | API (자연어 → 액션)
   │
   ▼
[액션 실행기] ── CaptureSource.execute()로 클릭·입력·포커스를 원본 페이지에 반영
```

**설계 포인트**

- **셸 독립 코어**: 구조추출·트리모델·뷰어·내비게이션·TTS·LLM은 "페이지에 어떻게 접근하는지" 모르는 순수 모듈. 페이지 접근/제어는 전부 `CaptureSource` 인터페이스 하나 뒤로 숨긴다.
- TTS 엔진과 LLM 엔진도 **추상화 인터페이스**로 두어 로컬/API를 쉽게 교체(플러그인 구조).
- 따라서 **A(확장) → C(데스크톱) 확장은 `CaptureSource` 구현 하나 + 셸 마운트만 추가**하면 되고, 코어·뷰어·엔진은 손대지 않는다.

### 4.1 캡처 어댑터 인터페이스 (유일한 교체 지점)

셸(A/C/개발용 B)이 다른 건 "페이지에 어떻게 접근·제어하느냐"뿐이다. 그 차이를 아래 인터페이스 하나로 격리해, 나머지 코드가 셸을 모르게 한다.

```ts
interface CaptureSource {
  getDOM(): Document | RemoteHandle;       // 라이브 DOM (A: 직접, C: CDP)
  getAXTree(): AXNode[];                    // 접근성 트리 (A: dom-accessibility-api / chrome.debugger, C: CDP getFullAXTree)
  execute(action: Action): Promise<void>;  // click/focus/input — 트러스트 핸들로 실행
  highlight(nodeId: string): void;         // 트리 노드 ↔ 화면 (A: getBoundingClientRect 오버레이, C: CDP Overlay.highlightNode)
  onMutation(cb: () => void): void;         // SPA 갱신 감지
}
```

| 구현 | 단계 | 페이지 접근 | 액션/트러스트 | 세션 |
|---|---|---|---|---|
| `ExtensionSource` | **1차 = MVP(A)** | content script | `.click()` (+필요 시 `chrome.debugger Input.*`) | 사용자 브라우저 그대로 |
| `PlaywrightSource` | 개발/벤치(B) | CDP(헤드리스) | CDP 트러스트 | 없음 — 코퍼스 채점용 |
| `DesktopSource` | **확장형(C)** | Electron+CDP | CDP 트러스트 | 영속 파티션 1회 로그인 |

> 교체 비용 = 새 `CaptureSource` 구현 1개 + 셸 마운트. TTS/LLM은 이미 각자 인터페이스라 A/C가 공유하고, 뷰어 컴포넌트도 셸에 mount만 바꿔 재사용한다.

## 5. 기술 스택 (초안)

| 영역 | 후보 |
|---|---|
| 페이지 접근/제어 (`CaptureSource`) | **1차: 브라우저 확장(Chrome MV3)** · 확장형: Electron+CDP · 개발/벤치: Playwright(헤드리스) |
| 구조 추출 | DOM 파서, Accessibility Tree(CDP), Readability, Turndown, 자체 휴리스틱 / **폴백**: ReaderLM-v2(로컬, 마크업 불량 사이트 전용 — CC-BY-NC 비상업 라이선스 주의) |
| TTS(로컬) | Piper, Coqui TTS 등 온디바이스 엔진 |
| TTS(API) | OpenAI TTS, ElevenLabs, Google/Azure TTS 등 |
| LLM(로컬) | Ollama(Llama·Qwen 등) |
| LLM(API) | OpenAI, Anthropic 등 |
| 입력 | 트랙패드 제스처 이벤트, 키보드 |
| 코어 | TypeScript(프론트/확장), 필요 시 Python(구조·모델 처리) |

> 대회 제출·심사에 유리하도록 라이선스는 관대한 오픈소스(MIT/Apache-2.0) 지향, 의존 라이브러리 라이선스 사전 검토.

## 6. 개발 로드맵 (A로 시작 → C로 확장)

> 모든 단계가 §4.1 `CaptureSource` 위에서 돈다. **Phase 1~5는 `ExtensionSource`(A) 하나로 완주**해 대회 MVP를 내고, C는 코어를 그대로 둔 채 어댑터+셸만 갈아끼우는 마지막 확장이다.

**Phase 1 — 코어 + 구조 추출 MVP**
- `CaptureSource` 인터페이스 확정. `PlaywrightSource`(B, 헤드리스)로 잘 마크업된 페이지에서 문서 트리 생성·콘솔 검증. (세션 불필요, 빠른 반복)

**Phase 2 — 확장 셸(A) + 내비게이션 + TTS**
- `ExtensionSource` 구현, 코어를 확장 사이드패널에 마운트. 트랙패드 훑기 + 레벨 이동(스페이스), 로컬 TTS, 음성 스타일. 트리 ↔ 화면 라이브 하이라이트.

**Phase 3 — 구조 보정 강화**
- 마크업 부실 페이지에 휴리스틱 + LLM 보정, 노이즈 제거. (B로 코퍼스 배치 벤치, A로 라이브 확인)

**Phase 4 — LLM 자연어 내비게이션**
- "로그인창 들어가줘" → 요소 탐색·액션 실행. 로컬/API LLM 스위칭. 로그인 가드레일(민감정보 로컬 강제 · CAPTCHA/2FA 사용자 인계 · 제출 전 확인). 교차출처 로그인 위젯은 `all_frames`+host 권한으로 보강.

**Phase 5 — 다듬기 = 대회 제출본**
- API TTS/LLM 옵션, 설정 UI, 실제 시각장애인 피드백, 데모 영상. **→ A 확장이 대회 MVP 산출물.**

**Phase 6 — C 확장 (여유 시)**
- `DesktopSource`(C) 추가: Electron+CDP, 영속 파티션 세션, 로컬 Piper/Ollama 서브프로세스, 스플릿뷰. **코어·뷰어·TTS·LLM·네비 로직은 재사용, 새로 짜는 건 `CaptureSource` 구현 1개 + Electron 셸뿐.**

## 7. 기대 효과 및 의의

- **탐색 효율**: 전체 구조 조망 → 원하는 곳으로 점프하는 방식으로 정보 도달 시간 단축.
- **낮은 진입 장벽**: 소수 제스처 + 자연어 명령으로 복잡한 단축키 학습 부담 완화.
- **청취 경험 개선**: 최신 자연스러운 음성으로 장시간 사용 피로 감소.
- **프라이버시 선택권**: 로컬 우선 모드로 민감한 페이지도 외부 전송 없이 이용.
- **오픈소스 기여**: 접근성이라는 사회적 가치 + 확장 가능한 플러그인 구조로 커뮤니티 참여 유도.

---

## 8. 리스크 및 검증 포인트

- **구조 추론 정확도**: 마크업이 나쁜 실제 사이트에서 트리 품질 — 다양한 사이트로 벤치마크 필요.
- **동적 페이지(SPA) 대응**: 콘텐츠 변경 감지 및 트리 갱신 전략.
- **제스처 정밀도**: 트랙패드 좌표→노드 매핑의 오차와 오작동 방지.
- **LLM 지연/비용**: 로컬 모델 성능과 API 지연·비용의 균형.
- **접근성 표준 준수**: 실제 시각장애인 사용자 테스트로 유용성 검증(가장 중요).

---

## 9. 차별화 요약 (심사용 한 문단)

기존 스크린리더가 "화면을 순서대로 읽는 도구"라면, 본 프로젝트는 **웹페이지를 의미 단위로 재구성해 계층적으로 탐색하게 하는 도구**다. 점자를 읽듯 트랙패드로 같은 레벨을 훑고 스페이스로 하위로 내려가는 직관적 조작, 최신 자연 음성과 스타일 선택, 그리고 "로그인창 들어가줘" 같은 자연어 명령(로컬·API LLM 모두 지원)을 결합해, 정보 접근의 **속도·이해도·편의성**을 동시에 끌어올린다.
